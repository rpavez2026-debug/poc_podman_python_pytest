Guía QA: Podman + FastAPI + PostgreSQL + Pytest

Qué hace este proyecto, cómo se arma el entorno y cómo se ejecutan las pruebas.

Python 3.12 FastAPI PostgreSQL 16 Podman 5 pytest + requests

1. Objetivo del proyecto

Es una prueba de concepto (POC) de automatización QA de APIs:

  • Una API REST hecha con FastAPI que hace un CRUD de usuarios.
  • Una base de datos PostgreSQL 16.
  • Las dos corren en contenedores Podman.
  • Las pruebas son pruebas de caja negra con pytest + requests: llaman a la API por HTTP como lo haría un cliente real y validan códigos de estado, contenido de la respuesta y que los datos queden guardados.

Los dos contenedores Podman están en la red qa-network.

  • La API se conecta a la base usando el nombre del contenedor (qa-postgres). Por eso ambos contenedores tienen que estar en la misma red de Podman (qa-network).
  • Desde tu máquina, la base se ve en el puerto 5433 (para psql o DBeaver) y cada versión de la API en un puerto distinto (8000, 8001, ...).

4. La API

Configuración

La API lee la conexión a la base desde variables de entorno:

VariableValor por defecto
DB_HOSTqa-postgres
DB_PORT5432
DB_NAMEqa_database
DB_USERqa_user
DB_PASSWORDvacío: hay que pasarla siempre

Endpoints

MétodoRutaÉxitoErrores
GET/health200 {"status": "OK"}—
GET/usuarios/{id}200 con el usuario404 no existe · 422 id no numérico · 503 base caída
POST/usuarios201 con el usuario creado409 email repetido · 422 datos inválidos · 503
PUT/usuarios/{id}200 con el usuario actualizado404 · 409 · 422 · 503
DELETE/usuarios/{id}204 sin cuerpo404 · 422 · 503

El cuerpo del POST y del PUT es el modelo UsuarioCrear:

{ "nombre": "QA Automatizador", "email": "qa@test.com", "activo": true }
  • email es de tipo EmailStr: si no es un email válido, FastAPI responde 422 sin llegar a la base de datos.
  • activo es opcional y por defecto vale true.
  • El PUT reemplaza todos los campos, así que hay que enviar el objeto completo.

Con la API levantada, la documentación interactiva (Swagger) está en http://127.0.0.1:<puerto>/docs.

5. La base de datos

La tabla usuarios tiene esta forma:

ColumnaTipoReglas
idintegerClave primaria, se genera sola (secuencia)
nombrevarchar(100)Obligatorio
emailvarchar(150)Obligatorio y UNIQUE: de aquí sale el 409
activobooleanPor defecto true

El proyecto todavía no tiene un script que la cree. Si arrancas desde cero, créala a mano:

CREATE TABLE usuarios (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(100) NOT NULL,
    email   VARCHAR(150) NOT NULL UNIQUE,
    activo  BOOLEAN DEFAULT TRUE
);

-- Usuario semilla que esperan test_api.py y test_api_postgres.py
INSERT INTO usuarios (nombre, email, activo)
VALUES ('Usuario QA', 'qa@test.com', TRUE);

El usuario con id = 1 es un dato fijo de prueba. Si un test lo borra o lo modifica, fallan test_api.py y test_api_postgres.py.

6. Levantar el entorno paso a paso

Todos los comandos se ejecutan desde la carpeta del proyecto.

  1. Levantar PostgreSQL

    podman compose up -d

  2. Crear la red compartida y conectar la base a ella (solo la primera vez)

    podman network create qa-network
podman network connect qa-network qa-postgres

  3. Crear la tabla y el usuario semilla (solo la primera vez; ver sección 5)

    podman exec -it qa-postgres psql -U qa_user -d qa_database

  4. Construir la imagen de la API. Sube el tag cada vez que cambies main.py.

    podman build -t poc-qa-api:1.5 -f Containerfile .

  5. Ejecutar la API en la red compartida, publicada en un puerto de tu máquina

    podman run -d --name qa-api-v5 --network qa-network \
  -p 8004:8000 -e DB_PASSWORD=qa_password_local poc-qa-api:1.5

  6. Comprobar que responde

    curl http://127.0.0.1:8004/health

7. Las pruebas

Preparación (una sola vez)

pip install pytest requests

Qué valida cada archivo

ArchivoPuertoQué valida
test_api.py8000Health check, consulta del usuario 1, id inválido (422), ruta inexistente (404)
test_api_postgres.py8001GET contra la base real: usuario existente (200), inexistente (404), id inválido (422)
test_api_post.py8002Creación (201) con verificación por GET, email duplicado (409), email inválido (422)
test_api_put.py8003Actualización (200) con verificación por GET, inexistente (404), email duplicado (409), 3 emails inválidos (422)

Cómo se ejecutan

# todo
pytest tests/

# un archivo, con detalle
pytest tests/test_api_put.py -v

# un solo test
pytest tests/test_api_put.py::test_actualizar_usuario_inexistente

# un caso de un parametrize
pytest "tests/test_api_put.py::test_actualizar_usuario_email_invalido[sin-arroba.com]"

# tests cuyo nombre contenga "duplicado"
pytest tests/ -k duplicado

Técnicas QA que se usan

  • Caja negra: los tests no importan código de la API, solo usan HTTP.
  • Partición de equivalencia y valores inválidos: con @pytest.mark.parametrize se prueban ids ("abc", "1.5", "null") y emails ("correo-invalido", "sin-arroba.com", "") inválidos.
  • Datos únicos por ejecución: los emails llevan uuid.uuid4().hex. Como los datos se guardan en el volumen, un email fijo daría 409 desde la segunda ejecución.
  • Verificar que se guardó: después de un POST o PUT, un GET confirma que el cambio llegó a la base.
  • Preparar los datos dentro del test: test_api_put.py usa el helper crear_usuario() para crear con POST el usuario que va a modificar, en vez de depender de datos fijos.

8. Problemas comunes

SíntomaCausa probableQué hacer
ConnectionError / Connection refused en pytestNo hay ninguna API en ese puertopodman ps y revisar el puerto del contenedor
503 Base de datos no disponibleLa API no llega a qa-postgres: falta la red, falta DB_PASSWORD o la base está apagadaRevisar --network qa-network y -e DB_PASSWORD=...; ver podman logs <contenedor>
El test espera 409 pero recibe 201La tabla no tiene UNIQUE en emailALTER TABLE usuarios ADD CONSTRAINT usuarios_email_key UNIQUE (email);
Falla un test del usuario 1El usuario semilla se borró o cambióVolver a insertarlo (sección 5)
Un cambio en main.py no se veEl contenedor usa la imagen anteriorReconstruir la imagen con un tag nuevo y levantar otro contenedor
La API no arranca: ImportError: email-validatorLa imagen se construyó antes de agregar la dependenciaReconstruir la imagen

9. Comandos útiles de Podman

# contenedores corriendo
podman ps

# logs de la API
podman logs -f qa-api-v5

# consola SQL
podman exec -it qa-postgres psql -U qa_user -d qa_database

# eliminar un contenedor
podman stop qa-api-v5 && podman rm qa-api-v5

# apagar Postgres (los datos se mantienen)
podman compose down

# apagar Postgres y BORRAR los datos
podman compose down -v
